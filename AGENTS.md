# AGENTS.md — roland-sticker-bot

## О проекте
Telegram-бот (pyTelegramBotAPI) конвертирует JPEG/PNG в EPS с контуром реза CutContour для плоттера Roland.
Состав: telegram_bot.py (бот + веб-админка + расчёт цены), jpeg2eps.py (конвертер), harvester/ (парсер и каталог), tests/.
Бот управляет реальным оборудованием (Hot Folder плоттера) и хранит файлы пользователей.

## Жёсткие запреты
- НИКОГДА не выводи в чат, логи, коммиты и файлы значения секретов (токены, пароли, UUID, ключи). Если нашёл секрет, назови только файл и строку.
- НЕ пиши в реальную папку Hot Folder. Для проверок используй временные каталоги (`tmp_path` в pytest).
- НЕ удаляй файлы и не переименовывай модули без явного пункта в задаче. Сначала спроси.
- НЕ добавляй новые зависимости без согласования. Если нужна, объясни зачем и предложи вариант без неё.

> [!NOTE]
> Запреты на сетевые команды/git push (ранее п. 2) и запуск сервисов/harvester/бота (ранее п. 3) сняты пользователем 15.10.2026.

## Правила работы
- Работай только в рамках текущей фазы. Всё, что выходит за неё, записывай в `TODO_NEXT.md` и не делай.
- Сначала план (что, в каких файлах, как проверю), потом код. Планы короткие.
- Маленькие шаги: один логический шаг = один коммит в ветке `fix/<фаза>`. Сообщение коммита: что и зачем.
- Большие файлы (telegram_bot.py ~2600 строк, jpeg2eps.py ~1900) читай диапазонами строк, не целиком.
- Поведение для пользователей не меняй, если задача этого не требует. Перед рефакторингом пиши тесты, фиксирующие текущее поведение.
- После каждого шага запускай `python -m pytest -q` и `python -m ruff check .`. Если не удалось запустить, так и скажи, не пиши, что тесты прошли.
- Никаких выдуманных результатов: если что-то не проверил, пиши «не проверено».

## Стиль кода
- Python 3.12+, типы в сигнатурах, `logging` вместо `print`, никаких голых `except Exception: pass` (минимум логировать).
- Все настройки (пути, IP, ID админов, пароли, цены) только через переменные окружения / config, без значений по умолчанию для секретов.
- Комментарии и сообщения пользователям на русском, имена в коде на английском.

## Формат отчёта в конце фазы
1. Что сделано (по пунктам, с файлами).
2. Что проверено и как (команды и результат).
3. Что НЕ проверено или осталось.
4. Что должен сделать человек вручную (ротация ключей, чистка git-истории и т.п.).

## Правила для веб-сервиса стикербомбинга

Структура (всё новое, существующий код не ломаем):
  sticker_app/    бэкенд (FastAPI), отдельный пакет
  web/            фронтенд (React + TypeScript + Vite + react-konva)
  docs/           контракты и решения (DATA_CONTRACT.md, COORDINATES.md, EXPORT.md, PROGRESS.md)
  tests/app/      тесты нового кода

Запрещено менять (только импортировать/читать): telegram_bot.py, jpeg2eps.py, harvester/*.
Если для задачи нужно изменить их, остановись и напиши предложение в docs/PROPOSALS.md, человек решит сам.
harvester.db открывать ТОЛЬКО в режиме read-only (sqlite3 URI mode=ro). Сервис пишет только в свою app.db.

Единицы и координаты (единый контракт, подробно в docs/COORDINATES.md):
- Единственный источник истины = миллиметры. Пиксели существуют только внутри отрисовки.
- Начало координат: левый верхний угол объекта, ось Y вниз, позиция стикера = его ЦЕНТР.
- Поворот в градусах по часовой стрелке вокруг центра стикера.
- Формат размещения: {asset_id, x_mm, y_mm, width_mm, rotation_deg, z, locked}.
  Высота выводится из пропорции исходника, не хранится отдельно.
- Преобразование px<->мм: функции в одном месте на каждый язык (web/src/geometry, sticker_app/geometry)
  с общими тестовыми векторами в tests/golden/geometry.json.

Контракты и совместимость:
- Версионируй схемы (design.schema.json, поле schema_version). Ломающие изменения делай только новой версией.
- API: префикс /api/v1, OpenAPI-схема в docs/openapi.json (генерируется), фронтенд-типы генерируются из неё.
- Перед изменением публичного контракта обнови docs и тесты, затем код.

Процесс:
- Один этап = одна ветка feature/<этап>, мелкие коммиты, в конце запись в docs/PROGRESS.md (что сделано, что проверено, что осталось).
- Каждый этап заканчивается зелёными pytest/ruff (бэкенд) и vitest/eslint/tsc (фронт). Если запустить не удалось, пиши «не проверено».
- Не добавляй зависимости без пункта в задаче. Для каждой новой зависимости объясни зачем и какая альтернатива.
- Не выдумывай данные. Если схема БД, пути или размеры неизвестны, запускай скрипт инспекции или спроси человека.
- Секреты только из окружения. Файлы пользователя в MVP не принимаем (нет загрузок).
- Публичные эндпоинты отдают макеты с usable_in_service = 1. По умолчанию (LICENSE_FILTER=off) это все макеты без takedown; LICENSE_FILTER=on оставляет только license own/licensed/cc0.
